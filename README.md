# avito-rag-search — поиск по статьям поддержки Авито

Поисковый пайплайн по базе справочных статей: на вход подается пользовательский запрос на русском, на выход — топ-10 релевантных статей. В качестве метрики качества выступает **MAP@10**.

**Итоговый результат: MAP@10 = 0.5136 на тестовом наборе.**

---

## Архитектура пайплайна


Два взаимодополняющих ретривера отбирают кандидатов: лексический BM25 ловит точные совпадения терминов, а dense-модель  перефразировки и запросы с опечатками. Их выдача объединяется через Reciprocal Rank Fusion, а финальный порядок задаёт cross-encoder — самая точная, но самая дорогая стадия, поэтому она работает только по узкому списку кандидатов. Скоры считаются на уровне чанков и агрегируются в скоры статей max-пулингом.

## Данные

- `data/candidate_public/articles.f` — статьи: `article_id`, `title`, `body` (HTML).
- `data/candidate_public/calibration.f` — размеченная валидация: 500 запросов, у каждого 1–2 релевантные статьи. Конвертируется в `data/queries.jsonl` скриптом `convert_val.py`.
- `data/candidate_public/test.f` — тестовые запросы; предсказания для сабмита пишутся в `data/answer.csv`.

Данные и индексы в git не попадают (`.gitignore`).

## Структура репозитория

```
.

│   ├── preprocess.py         # HTML -> текст -> чанки -> parquet
│   ├── convert_val.py        # calibration.f -> queries.jsonl
```

## Quickstart

Требования: Python 3.14+, [uv](https://docs.astral.sh/uv/). Для реранкера нужна GPU: на T4 в fp16 — секунды на запрос, на CPU cross-encoder непрактичен (~100 с/запрос).

```bash
uv sync --group dense   # dense-группа: sentence-transformers + faiss

# все скрипты запускаются из scripts/ — пути в конфиге заданы относительно неё
cd scripts

# 1. Препроцессинг: HTML -> чанки с заголовками -> data/processed.parquet
uv run python preprocess.py

# 2. Конвертация валидации в jsonl
uv run python convert_val.py

# 3. Построение индексов
uv run python index.py --retriever all

# 4. Оценка на калибровке: MAP@10 + latency
uv run python evaluate.py --retriever bm25      # random | bm25 | dense | hybrid | reranker
uv run python evaluate.py --retriever reranker

# 5. Сабмит
uv run python answer.py --retriever reranker
```

## Конфигурация

Все параметры собраны в `config.yaml` то есть эксперименты не требуют правки кода. Финальные значения:

| Параметр | Значение | Комментарий |
|---|---|---|
| chunk_size / chunk_overlap | 180 / 40 слов | чанк + заголовок влезают в контекст моделей: русский текст — ~1.5–2 токена/слово |
| embedding | intfloat/multilingual-e5-large | обязательны префиксы `query:` / `passage:` |
| reranker | BAAI/bge-reranker-v2-m3 | fp16 (`model.half()`) — ускорение в разы без потери качества |
| candidate_chunks | 250 | глубина выдачи каждого ретривера до фьюжна |
| rrf_k | 60 | константа RRF |
| rerank_candidates | 100 | сколько пар видит cross-encoder |
| aggregation | max | пулинг чанк-скоров в скор статьи |
| top_k | 10 | размер финальной выдачи |

## Результаты

Все прогоны логируются в `logs/logs.txt` с таймстемпом, метрикой, latency и полным поисковым конфигом. Ключевые точки на калибровке (500 запросов):

| Конфигурация | MAP@10 | Latency, мс/запрос |
|---|---|---|
| Random baseline (санити-чек) | 0.010 | <1 |
| BM25, чанки 300/50 | 0.274 | ~7 |
| Dense e5-large, чанки 300/50 | 0.348 | ~189 |
| Hybrid RRF (BM25 + dense), чанки 300/50 | 0.418 | ~198 |
| BM25, чанки 180/40 + title в чанке | 0.290 | ~11 |
| **Финал: Hybrid + reranker (fp16), чанки 180/40 + title — тест** | **0.514** | GPU T4 |

Прогрессия по стадиям: dense даёт +7 пунктов к BM25, гибрид — ещё +7 к dense, реранкер поверх гибрида — основной вклад в финальную цифру, что ожидаемо для MAP@10: при 1–2 релевантах на запрос метрика почти вырождается в MRR и определяется позицией нужной статьи в топ-1–3, а именно порядок внутри топа cross-encoder исправляет лучше всего.

## Ключевые инженерные решения

**Заголовок в каждом чанке (+1.6 пункта уже на BM25).** Заголовки справочных статей («Понять, что профиль заблокирован») часто почти дословно совпадают с запросом, поэтому title приклеивается к началу каждого чанка — он гарантированно попадает и в эмбеддинг, и в пары реранкера даже при обрезке хвоста.

**Размер чанка выбран из бюджета токенов, а не «на глаз».** При чанках в 300 слов (~450–600 токенов в мультиязычном токенизаторе) тексты молча обрезались и e5, и реранкером. Переход на 180 слов устранил обрезку и заодно ускорил cross-encoder т.к. attention квадратичен по длине.

**fp16 на T4.** Cross-encoder в fp32 считает ~8 с/запрос. Каст модели в `half()` задействует тензорные ядра T4 и снижает время в разы без изменения качества ранжирования.

**Агрегация max против mean top-k.** Проверено на калибровке: mean top-3 проседает и на BM25 (0.244 против 0.274), и на dense (0.309 против 0.348) — для коротких запросов статью надёжнее представляет её лучший чанк, а не среднее.

**ranx вместо самописного MAP.** Метрика считается библиотекой, т.к. во время самописного написания можно было нахватать лишних ошибок и потерять ограниченное время на их отлов. 

**Кэш лемм pymorphy3.** Лемматизация без кэша делает индексацию корпуса медленной, а словарный кэш сводит её к секундам.

## Findings — что показал анализ

- **Лексика vs семантика.** BM25 силён на запросах с точной терминологией домена, а dense вытягивает перефразировки и опечатки. Гибрид покрывает оба режима, отсюда его стабильный отрыв от каждого ретривера в одиночку.
- **Шум в запросах.** Приветствия и плейсхолдеры (`<DATE>`, `<MONEY>`) разбавляют и без того короткие запросы, а их чистка перед поиском это ближайший дешёвый источник прироста.
- **Реранкер** при малом числе релевантов на запрос: он видит запрос и пассаж совместно и исправляет порядок в топе, к которому метрика наиболее чувствительна.
- **Префиксы e5 обязательны.** Без `query:` / `passage:` модель работает, но тихо теряет качество — проверяется в первую очередь при отладке dense-стадии.
